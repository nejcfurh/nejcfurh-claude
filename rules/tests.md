# Testing Standards

**When to apply:** editing test files (`*.test.ts(x)`, `*.spec.ts(x)`).

- Use the project's existing test runner and patterns — don't introduce a new one.
- Test behavior, not implementation details — a refactor that preserves behavior must not break the test. Heuristic: if you could rewrite the implementation and the test still passes for the wrong reason (or would pass against no implementation at all), it asserts nothing.
- Mock external dependencies only (APIs, databases, file system) — not internal modules.
- Each test independent — no shared mutable state between tests.
- No hardcoded data coupled to environment — use factories or builders.
- `describe`/`it` names that read as sentences.
- Run the single relevant test file during development; full suite before declaring done.
- A flaky test gets fixed or removed, never ignored. If it will not reproduce locally in ~3 attempts, stop looping the suite and **push it to CI** — a matrix leg on another OS often reproduces deterministically what your machine hides. Looping locally dozens of times is the expensive way to learn nothing.
- Assert on values normalised the way the code under test derives them. A test that compares a path must canonicalise it identically (`cd … && pwd`, not the raw `mktemp` string): `TMPDIR` may carry a trailing slash, so `mktemp -d "$TMPDIR/x"` can return a double slash that the code under test collapses. Environment shape — trailing slashes, temp dirs reached through a symlink, BSD vs GNU flags — is where "passes locally, fails on CI" comes from.
- **A state probe that returns immediately is not a wait.** Browser-automation APIs split into auto-waiting assertions and instant probes that answer only about the current tick — Playwright's `locator.isVisible()` is the classic trap, because it *accepts a `timeout` option*, which reads like it waits, and doesn't. Point it at anything that arrives via a client fetch and it reports `false` before the response lands, so a working feature fails its own test. The dangerous half is the inverse: the identical call on a "should be absent" assertion also returns `false` and therefore **passes**, certifying a broken feature. Use the waiting form (`waitFor({ state })`, `expect(locator).toBeVisible()`). And when a batch of assertions fails at once, suspect the harness before the product — an impossible companion reading (an interception counter still at zero, an elapsed time of 0.0s) is the tell that nothing was ever measured.
- **Visible is not interactive, and rendered is not hydrated.** An element can be on screen with no handler attached yet, so a click lands, does nothing, and the assertion after it passes for the wrong reason. Before trusting the result of any interaction, confirm the interaction *happened*: the request it should have fired, the state that should have flipped, the label that should have changed. A proof of an interaction that never ran is the same failure as an instant probe, one layer up.
- **`innerText` is rendered text; `textContent` is source text.** `innerText` honours CSS — `text-transform: uppercase` hands back the string uppercased, a hidden element hands back nothing — so comparing it against the literal in your source fails for copy that is on screen and correct. Case-fold both sides, or read `textContent`. Same trap for any interpolated value: a template holding a `{placeholder}` never appears verbatim anywhere, so match the literal segments around the placeholder instead. And check the viewport a string actually renders in — a mobile-only element measured at desktop width is absent because you never asked for it. Every one of these produces a false *negative*, which arrives dressed as a list of real defects.
- **A passing DOM assertion is not visual verification.** Asserting that an element exists, or that an anchor is absent, says nothing about whether the result looks right — a fallback can inherit link styling and still read as clickable, text can overflow into the next column, an inert value can be exposed to the user verbatim. All three pass a DOM check and are obvious in a screenshot. For any change that alters what renders, look at the rendered artifact before calling it verified; the assertions decide whether to look closer, they do not replace looking.
- **A test that injects the end state cannot prove the transition into it.** Passing the settled condition in as a prop, fixture or seeded value — `status: 'busy'`, an already-disabled control, a pre-populated cache — proves only that the code behaves correctly *once there*. The bug usually lives in getting there: a guard that depends on a state update lands a render late, so two events in the same tick both pass. Such a test is doubly misleading because its name describes the behaviour you wanted ("blocks a second submit"), so a later reader takes the green as a guarantee it never made. Drive the real entry point and count the effects — requests issued, rows written, handler invocations — rather than asserting on the state you supplied yourself.
- E2E against shared state (PostHog sandbox flags, shared test accounts, seeded catalogs) may only mutate namespaced entities the test itself created (e.g. `e2e-*` prefixed), must never edit or select-by-fallback into real/shared entities, and must end by verifying the shared state is restored byte-identical. A conflict/deletion test needs an explicit re-select of its own entity — UI fallback selection after a delete is how a test silently edits the wrong record.
- **Tests that mint a single-use credential for one shared account cannot run in parallel.** Magic links, recovery tokens, OTPs and password-reset links are usually invalidated by issuing the next one, so N parallel workers signing in as the same user leave one winner and N-1 failures — in the setup step, before any assertion runs. The tell is a partial pass whose failures are all at the sign-in await and whose messages have nothing to do with the feature. Either give each worker its own account, or pin the file to one worker (a serial describe block or a workers-1 run). Diagnose it before rerunning: an auth race and a genuinely broken feature look identical from the failure count, and a rerun that happens to interleave differently will "fix" it and teach you the wrong thing.
