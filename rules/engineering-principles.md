# Engineering Principles

**When to apply:** every implementation task.

## Change sizing

- Target small, reviewable commits (~100 lines); up to ~300 for cohesive changes that can't be split without losing context.
- 1000+ line changes must be split into sequential PRs or stacked commits.
- PRs touching 15+ files need a reason (rename/migration is fine; "I was in the area" is not).
- Past ~30 files or ~1000 lines, the answer is a **stack**, not a bigger PR — and so it is whenever new work depends on a PR that is already open. Reviewability is the constraint being optimised, not PR count. Mechanics, slicing order and the seam test: `git-conventions.md`.

## Branching complexity

Cyclomatic complexity is decision points + 1 — every `if`, `else if`, `case`, loop, `catch`, ternary, and each `&&`/`||` in a condition. **The project's own config wins**: an eslint `complexity` rule, a radon or sonar threshold, a `gocyclo` flag in CI is the number to work to. Absent one: 1-5 fine, 6-10 refactor-if-already-in-the-file, 11-15 refactor now, past 15 split before the change lands.

Measure rather than eyeball — the eyeballed estimate runs low: `radon cc -s -a <path>` for Python, `gocyclo <path>` for Go, `lizard <path>` for most anything else, eslint's `complexity` rule for JS/TS (its one-off `--rule` form differs between eslint 8 and flat config). Where no tool is installed, count by hand and show the count per function.

Tactics, in order: guard clauses that invert and return early; extract a function whose name states *what*, not *how*; a lookup table in place of an if-else or switch chain; a named predicate instead of a four-clause boolean; extract the loop body and `continue` instead of nesting. Strategy or polymorphism for a switch-on-type only once that same switch appears in two or more places.

Two failure modes matter more than the score. **Don't game the metric** — a dense one-liner hiding six branches scores better than the honest if-chain and reads worse, so complexity has to move into named units rather than disappear into cleverness. And **the count triggers a look, it never delivers a verdict**: splitting a linear dispatch into six functions lowers the number and can hurt the reader.

Lowering a count is behaviour-neutral by definition, so the existing tests must pass against **both** versions (`tests.md`), and a refactor with no test over it either gets one first or stays small enough to read in one sitting. Never change an exported signature to lower a count without asking. A function over the threshold that the task does not otherwise touch is a note in the PR body, not an edit. A before/after count in a PR body is a durable number, so *Measuring a change* applies — including reverting when the result reads worse.

## Vertical slicing

Implement features as thin end-to-end slices (UI + API + DB + test for one path), not horizontal layers ("all models first, then all routes"). If a slice is too large, narrow the scope — fewer fields, simpler validation.

## A handed file may be a model, not the target

When a request supplies standalone artifacts — a mockup, an exported page, a prototype, a design file — and the working directory is a codebase, establish which is the deliverable **before editing either**. Paths in the prompt read as the target and are often only the reference. The tell is a sentence locating the thing elsewhere: "the design we have in the app", "like the one in production", "match what's live" — an implementation already exists and the handed file describes it; one search for the artifact's distinctive strings settles it. Getting this wrong is expensive because nothing fails: editing the artifact succeeds, the diff looks right, and every check passes, since the file is in no build — until someone asks to see the result running.

## Chesterton's Fence

Before removing or changing existing code, understand why it exists: `git blame`, the introducing commit message, linked PRs. If no context exists and the code seems unnecessary, ask — don't silently remove.

**The fence cuts the other way too: an exception to a standing rule is a fence with a date on it.** A runbook step, a code comment or a test assertion that grants an exception — "this one is changed by hand in production", "this check is skipped here" — reads as current procedure because it is written down, and is often a leftover from a migration or cutover that has since closed. Before following one, read where it came from: blame on the line, the change that introduced it, the ticket it names. When it contradicts a standing rule, the contradiction is the finding: ask the rule's owner which one is current. Never resolve it by handing the forbidden action to a person able to do it — that routes around the rule while looking like compliance, and writes a stale procedure into a ticket where the next reader takes it as settled.

## Shift left

Catch problems as early as possible: type system > lint > unit tests > integration tests > runtime validation > monitoring. If the type system can catch it, don't write a test for it — fix the types.

**A missing config value must never silently select the branch that disables the feature.** Environment-driven gates — a kill switch, a sampling flag, an "only outside local development" guard — get a fallback for the unset case that reads as the conservative choice. It isn't: the feature ships, everything builds, no error appears, and the code is inert in exactly the environment it was written for, because a disabled feature emits nothing to notice. Absence means unknown, not off: fail loudly at startup, or default to the branch whose wrongness is visible, and have the deploy make the value explicit. A gate copied from somewhere it already works brings its env vars — port the deployment configuration in the same change, and read back what the running build actually resolved.

## Self-contained fallback and loading states

Anything meant to render before the page/app finishes loading — a spinner, a Suspense/skeleton fallback, a splash screen — must not depend on the assets it exists to cover for. Styling it with the same utility classes as everything else is the natural default and wrong here: under a slow connection the stylesheet (or an animation's keyframes) may not have loaded at first paint, so it renders as an invisible, unstyled element in the one place that can't assume its assets are present. Use inline styles for what matters (colour, dimensions, border) and a scoped `<style>` tag with `@keyframes` — not a utility animation class — for anything that must be visible from the first paint. Once a loading state runs *after* hydration, style it normally.

## Grep before you build, grep before you're done

Two checks belong around every fix that targets a *pattern* rather than a single call site:

- **Before building:** grep for how the same *class* of problem is already solved elsewhere before inventing a new mechanism. A codebase with an established fix for "this event must survive a page unload" or "this write must be idempotent" is telling you the shape of the fix it expects; a fresh undocumented approach next to three existing ones is what a reviewer catches and a search would have.
- **Before declaring done:** grep for the literal pattern you just fixed, not just the file you noticed it in. A bug description phrased as "X does Y" is a search query — sibling files (a paired error boundary, a duplicated handler, a copy-pasted route) routinely carry the identical defect.

**Grep the history too, when the thing you are adding used to exist.** A request to put back behaviour a recent rewrite removed — a link, a badge, a field, a tracking parameter — is a restoration, and the deleted implementation is its specification. It carries decisions the request will not restate: which identifier an outbound link tagged, whether it opened in a new tab, which case it deliberately skipped. Rebuilt from the current tree alone, the result looks complete and silently drops every one of them. The tell is in the rewrite's own diff — a file that owned the behaviour is gone (`git log --diff-filter=D -- <area>`, or the `--stat` of the merge you pulled). Read that version first and say which of its decisions you kept.

**The same history read comes before proposing a fix for a regression.** When `git log -S` or blame shows the bug's mechanism arrived with a recent rewrite, read the version before it first: the mechanism the rewrite removed is the first fix candidate, and usually the simplest. Skip that read and every option you put to the user is built on top of the rewrite's mistake — each plausible, none of them "undo the part that broke it".

**The same check applies before scripting against the project's own systems, and is skipped more often there.** Driving a sign-in, seeding a fixture, minting a token, standing up a test double feel like plumbing, so the instinct is the upstream tool's docs. The project has almost always solved it, and its test helpers hold the working sequence: which endpoint establishes a session, which parameter the callback needs, which of two plausible flows does not silently no-op. Each wrong guess costs a whole round, because it looks like a product bug — a redirect to sign-in, an empty render, a 401 — rather than a harness that was never going to work.

**The file you copied from is one sample, not the convention.** Cloning the nearest neighbour silently adopts that one file's choices, including the ones nobody else makes. Count before you copy: list every sibling that solves the same problem and see which way the majority goes; where they disagree, the newest and the most-depended-on are the better guides. This bites hardest on things with no visible failure — how config is validated, whether a boundary throws or returns empty, what a missing value defaults to — because the outlier passes its tests exactly like the convention does.

## Blast radius on production

Before running or recommending a bulk operation — a backfill, migration loop, or mass API job — against a shared, rate-limited production resource (a live third-party API like Stripe, a DB connection pool), estimate peak load = concurrency × per-item fan-out and keep it a small fraction of the budget so customer-facing traffic isn't starved. Start conservative and ramp; never launch a prod batch at high concurrency. An admin/batch job must never degrade a customer path.

The same check applies below "bulk": a single scripted action that creates real records or triggers a real paid API call on shared infrastructure carries the same disclosure obligation — the trigger is "does this have a real side effect", not "how many iterations". A preview or staging environment the user just stood up is not exempt. Flag it before the first run, not after several have landed.

**Pilot every item of a batch once before running the batch.** Before fanning out N slow or quota-drawing runs — headless sessions, CI jobs, paid API calls — run each distinct item once and read its duration, output size and result shape. One runaway item (a reply that writes to the output limit, a run that dies at a turn cap) otherwise multiplies into the whole batch's time and quota, and an item that cannot produce a meaningful result is only discovered after all of it was paid for.

## Copying data is a disclosure decision

Pulling a dataset out of a shared environment onto someone's machine is its own decision, separate from whatever you needed it for, and it is made on what the data *contains* — so find out before describing it.

**A schema-scoped export is not a PII-scoped export.** Excluding an auth or identity schema does not make an extract clean: application tables carry their own email, name, phone and address columns, and audit or event-log tables are usually the worst. Enumerate the columns (`information_schema.columns` filtered on the obvious names) and grep the produced file before claiming anything about it. Never present a scoping choice as a privacy guarantee — if someone accepts a copy because you said it carried nothing sensitive, an inaccurate summary made that decision for them. State what it contains, where it landed, and that it is ignored by version control rather than absent from disk. Prefer the least-sensitive source and a target you can name over a schema sweep; when the data only needs to make a screen render, a synthetic fixture beats a real extract.

## Anti-rationalization

Never accept these shortcuts:

| Shortcut | Why it's wrong |
| --- | --- |
| Skip tests ("too simple to break") | Simple code becomes complex; the test catches the regression |
| `any` type ("fix later") | Later never comes; `any` spreads |
| Skip error handling ("can't fail") | Everything can fail |
| Hardcode values ("just for now") | Hardcoded values become permanent |
| TODO without a ticket | Dead code; ticket it or fix it now |
| Copy-paste with tweaks | Duplication diverges; extract or accept repetition consciously |

## A noticed concern is a debt, not a thought

The most expensive misses are the ones you *did* see, phrased as "worth checking" or "I'll note that in the write-up", and never discharged. The noticing feels like handling it, so the item is silently marked done — and because you already considered it, you will not reconsider it.

- **A check you decided to run.** Run it then, or say out loud that you skipped it and why. "I should confirm nothing else is using this before I overwrite it" is worthless one command later.
- **A trade-off you decided to record.** Put it in the artifact — the PR body, the ticket, the handover — when you notice it. A caveat that lives only in your reasoning does not exist for anyone else, and a reviewer finding it later reads it as hidden rather than weighed.

Treat "I'll come back to that" as a commitment with no scheduler behind it.

**Route the debt by ownership** — a concern about work the current task does not own goes to the durable store, not to the user. Housekeeping is where this bites: tidying notes, indexes or docs surfaces findings about *other* work items, and escalating one mid-task is scope drift wearing the costume of diligence — it interrupts the work under review and hands over an action item with none of its scrutiny. Write it where that work will be picked up (its ticket, its notes, the memory entry). Raise it in conversation only when it blocks the current task or is time-critical, and verify it to the task's standard first.

## Verifying a change

**Closing an item as already-done is a claim about scope, not just presence.** Confirming the named change landed — the version bumped, the commit merged, the flag flipped — says nothing about *coverage*: that the bump cleared both affected surfaces, that the fix reached every caller, that the migration covered every environment. Verify the scope the closure note will claim. On most trackers that note is append-only and reads to the next person as a verified finding rather than a repeated assumption.

**A gate you add is verified through the path that actually invokes it, and priced before it ships.** A guard's whole value is behaviour at a moment you are not watching, so a suite that calls it directly can pass on a version that never fires in production. A hand-built input encodes the assumptions under test — the working directory, the argument form, the environment — and those are exactly where guards fail open. Drive it once end to end, from the real entry point, with a case that must be refused; a guard that should have blocked returns the operation's own output, which reads as success. Then price it: it usually hangs off a dispatcher that runs far more often than what it guards, so route it under the condition it checks and measure the per-call difference, since nobody attributes a slow session to a hook.

**Spending one of several independent locks is a trade, never a free simplification.** Safety often rests on two things being true at once — a flag still narrow *and* a switch still unset, a code guard *and* a credential nobody has issued. When a change spends one ahead of need, say which single point of failure the remaining one now is, and prefer splitting the change so each lock is spent when actually required. The argument that the surviving lock holds is usually correct and beside the point: nothing catches the mistake if someone flips the wrong thing tomorrow.

**Launch readiness includes the words.** Check every sentence the user reads — UI, email, brief — against what the test run actually did, on each branch of the logic. A test observation that contradicts the copy is a defect even when it matches the code, and "working as implemented" is exactly the verdict that lets it through. A plan item marked unresolved blocks readiness until its owner decides: carried forward silently, an open question becomes a shipped answer nobody chose.

**A check must be derived independently of the change.** Build it from a different starting point than the edit — a different pattern shape, a different layer, or the rendered/deployed output rather than the source you touched. A grep reusing the fix's own pattern, a test asserting the same constant the code maps over, a delegate's search that pre-filtered out the files in question: all confirm the assumption instead of testing the result, and come back green. The check that finds the miss is almost always the one built a different way.

**An enumeration that backs a go/no-go is produced by a command, not by recall.** "Everything this change does in production", "the files affected", "nothing else is touched" — a list assembled from your own earlier reading is not one derived from the diff, and the item you already looked at and judged minor is the one that drops out. Enumerate mechanically, then classify every entry against the claim — gated or not, reachable or not. If answering a challenge requires running that command, you never had the answer, only a recollection of having had it.

**Truncated output is a partial read — re-query, don't report it.** Tools elide long values mid-field, so the row still looks like a row. Re-query: project fewer columns, filter to the rows in question, or aggregate down to what the comparison needs. "Appears to match, output truncated" is not enough once that row feeds a table someone decides from — the unread cell is exactly where a difference would hide.

**Never state what CI does or does not run without reading the trigger.** "The integration suite covers this on the PR" is a claim about a config file. Jobs are narrowed by branch filters, path filters, `workflow_dispatch`-only triggers or `if:` conditions, so a job that exists is not a job that ran. Read the trigger block against `git diff --name-only`. Get it wrong and you have told a reviewer a class of verification happened when it did not, in a sentence that usually lands in the PR description; prefer reporting the checks you actually saw on the PR.

**A default-UA fetch is not what a user receives.** Servers branch on the user agent — bot detection, analytics suppression, differing markup — so a plain command-line request can return a document missing whole blocks a browser would get. "The string is absent from the HTML" is not evidence until the request carried a real browser UA; this failure is a *false negative*, which arrives dressed as a clean result. Inversely, a value the page consumes and replaces at runtime reads as missing after load. Check the served document for what the server sent and the live DOM for what survives — never conclude from only one.

An unverified change is cheaper than a wrongly verified one, because a green check gets reported as fact and is believed. "I verified it" is a claim about the *method*: if the method could not have failed, it did not verify anything.

**Migrating literals into an indirection layer needs a reachability check, not an equivalence check.** When strings, numbers or settings move behind a lookup — a message dictionary, a flag registry, a config map, a theme table — "does the old surface still render the same" is blind to the one failure the migration introduces: a **key created but never wired**, whose call site still holds the original literal. The old value renders because it is still hardcoded, so the check passes most confidently on exactly the entries that were missed. Verify the other direction: parse the keys out of the lookup, grep each against its own source file, and treat any with no reference as unmigrated (confirm computed or templated keys rather than assuming). Otherwise the leftovers surface as the original language or old default on whichever surface someone opens first.

**Proving a new test can fail requires a harness valid for BOTH versions.** A test that passes before and after asserts nothing about the change, so running it against the old code is right — but only if the *only* difference is the code under test. A new test pointed at the old implementation often fails for harness reasons: a mock written against the new module's imports, a fixture that did not exist yet, a renamed export. That red reads exactly like the proof you wanted. An import, type or "not a function" error is a broken harness, not a behavioural difference; fill in what the old version needs, stubbed to what production does, and re-run. Inversely, for a behaviour-neutral change, passing against *both* versions is the proof.

**Revert a deliberate mutation from a snapshot you took, not from version control.** `git checkout -- <path>` restores what is *committed* — neither the file you created and have not committed nor the unrelated uncommitted edits in the same path. It discards both silently, and the next mutation stacks on a tree you no longer recognise while every round still produces a plausible-looking failure. `cp` the files aside before the first mutation, copy them back between rounds, and diff against the snapshot at the end.

**A command's exit status is not the pipeline's.** `cmd | tail -n5` reports *tail's* status, so an `echo "exit:$?"` after it prints success however `cmd` failed — and a `--quiet` flag hides the error text that would have given it away. Together they make a check that cannot fail. Confirm an install, build or migration from the **artifact** it should produce — the directory is populated, the binary resolves, the row exists. A dependency tree that never installed reappears as a wall of unrelated compile errors, the wrong thing gets debugged, and anyone you hand the claim to, including a delegate, builds on it rather than re-checking it.

**A callback you hand to a dependency runs under that dependency's error handling, not yours.** Before adding a function to a third-party extension point — a before-send filter, a request interceptor, a lifecycle hook, a custom serializer — read the call site in the *installed* package and find out whether the host wraps it. Many do not: one throw from your function takes out everything downstream, far wider than the feature you were adding. Size the blast radius from the call site, not from your function's purpose. Make it fail open and prove it with hostile inputs — nulls, wrong types, missing keys at every level the payload nests. "I traced the branches and there is no throw path" is a deduction about your reading; the payload's shape belongs to the dependency, which is free to change it.

**Patching a global is invisible to any consumer that already captured the reference.** Libraries routinely bind `fetch`, `XMLHttpRequest`, `setTimeout` or a logger into module scope when their bundle evaluates, so reassigning the global afterwards — from a console snippet, a test hook, an injected probe — is never consulted by them. Prototype methods and per-call lookups still intercept; a captured reference does not. Read how the installed package takes the reference first: the patch installs, reports success, and observes nothing.

That sets the bar for validating an interceptor: **exercise it with traffic the dependency itself generates, never with a call you synthesise.** A hand-made request goes down a path the probe can see by construction, so it proves the parser and nothing else, and passes most confidently when the real transport is the one being missed. If you cannot make the dependency emit through the probe, you have not built a probe — say so.

**A state occurring a few dozen times a day across a whole population will not reproduce to order.** Before designing a hunt that depends on landing in a rare state — asking someone to walk flows, scripting a sequence, watching a live session — estimate the hit probability: occurrences per day against total traffic, times the attempts you will actually make. When it is small, hand-reproduction is a lottery and a clean run tells you nothing. Instrument the population instead: ship the assertion that reports the state wherever it happens, and read it a day later. A production report names the call site; a failed reproduction does not even bound the problem.

**A recording, log or dump you were handed is a measuring instrument — exhaust it before building a reproduction.** A screen capture carries timestamps and pixel coordinates, a log carries ordering and intervals, a dump carries exact values. Fitting that artifact against what the code *intended* often names the fault outright — a constant scale factor, a fixed offset, an off-by-one interval — for the cost of one script, where an environment costs installs, servers and sometimes someone's foreground apps, and answers nothing when the fault does not reproduce there. The tell that you skipped this: several rounds of environment-building, then one calculation over the original artifact that settles it.

**A report's "it worked before X" is a search constraint, so check it before it steers anything.** The offered boundary — a release, a merge, a device, a settings change — silently scopes every hypothesis you form next, and is cheap to test: one `git log -L` over the lines producing the symptom says whether they moved at all. If they never changed, the cause is environmental and every theory about a recent change is dead on arrival — the most valuable thing you can learn in the first minute. The reporter is telling you when *they* noticed, not when the behaviour changed.

**"It happens on X but not on Y" is the experiment, already designed.** A report that scopes itself — this screen and not that one, this platform, this account and not a colleague's — hands you a control group, and the cause is whatever differs between them. Diff the pair first: the two screens' props, the two configs, the two environments. That usually lands on the mechanism in one command. The discriminator arrives as a parenthetical aside — where the reporter *also* checked — which makes it the easiest sentence to read past.

**Establish the request path before theorising about the origin.** A fault on one hostname and not another is a claim about the *route*: a CDN, WAF or proxy in front of the origin can alter or reject a request the origin handles perfectly, and nothing in the repo records that it is there. The response headers usually say so — the tell is a header from a vendor nobody deployed in the code. Bisect it in one command: repeat the identical request resolved straight to the origin (`curl --resolve <host>:443:<origin-ip> …`). If it succeeds there and fails through the front door, the application is exonerated, and every theory about its code, assets or caches is dead.

**Consistency is not correctness — establish the current value is wrong before changing it to match.** Bringing an outlier into line invites the wrong verification: you measure that the new value matches its neighbours, a check that cannot fail because you chose the target. It also cannot tell a defect from a deliberate exception — a size tuned for that surface, a spacing the design asked for, a threshold someone set after seeing it. Say what is *wrong* with the value and where you observed it; if the only complaint is that it differs, the case is not made. Otherwise whoever accepted the old behaviour gets a regression alongside the fix they wanted.

**Authoring a file through the shell bypasses whatever the editor tools trigger.** Projects commonly hang formatting, linting or codegen off file-editing tool calls. A file created with a redirect, a heredoc or a generator script is invisible to those hooks, so it lands unformatted and the omission surfaces much later — at a pre-push gate or in CI, on a branch you believed was clean. Run the project's formatter over such files before staging.

**Modifying an existing file is a different act from creating one, and the shell is the wrong default for it.** Heredocs and inline scripts suit new files, large payloads and batches. Changing a handful of lines in an existing file that way trades a targeted edit for a pattern-driven rewrite, and the failure is a *plausible* result: a capture group one line too far, the wrong one of two similar blocks, a scope's closing lines dropped. Prefer the editing tools, which fail loudly on an ambiguous or unmatched target. A shell replacement that matches nothing is the quieter half: it exits cleanly, prints nothing, and the next thing you say about that file is wrong. The target also goes stale between read and replace — an on-edit hook rewrote the line, or you typed the old value from memory. Where the shell is genuinely right, address by line, snapshot first, read the result back, and treat "no output" as unproven. Either way, confirm the file still parses.

**Never assume the shell's working directory — write paths that do not depend on it.** Whether a `cd` survives to the next command is a property of the harness, not the shell, and it differs between them. Assuming it persisted sends the next command to the wrong tree, where a relative path misses or hits a same-named file in another checkout; assuming it reset makes a relative re-`cd` fail. Use absolute paths, or put the `cd` in the same command. In a repo, prefer `git -C <path>`. Where the cwd matters, print it.

**The same applies to every path that comes from the environment rather than from you, and a sandbox boundary is where it bites.** `$TMPDIR` is resolved by whatever executes the command, so the same variable names different directories sandboxed and unsandboxed. A file written through one invocation and read through the other is simply missing, with an error that reads as a vanished file — and both commands look identical. Any file that must outlive one invocation gets an absolute path you chose. (Backed by the tmpdir-sandbox gate, which warns when a command running outside the sandbox names `$TMPDIR`.)

**zsh is not bash about variables, and the difference fails quietly.** An unquoted `$var` holding spaces is *not* word-split, so `set -- $pair` yields one argument instead of two; use `${=var}`. And `$name:x` applies a history modifier — `$2:rate` becomes `$2` with its extension stripped, followed by `ate` — so brace every variable a colon follows: `${2}:rate`. Both run and do the wrong thing, which reads as a bug in the tool being driven; when a scripted sweep returns identical readings for every case, check the loop variables first.

**A heredoc is only literal when its delimiter is quoted.** `<<EOF` expands the body as the shell would: backticks run as commands and `$name` is substituted before your program sees the text, so a Markdown body turns into "command not found" errors and a document with holes. Write `<<'EOF'` whenever the body is meant verbatim. Chain the publishing step to the preparing step with `&&`, never a newline or `;` — when preparation fails, a separate line still publishes the stale version, reported as success.

## Measuring a change

Applies whenever a number **or a verdict** decides whether a change is good — perf work, output quality, anything tuned against a metric rather than a passing test, and any script that sweeps for a condition and reports what it found.

- **Validate the metric before trusting it.** Run it on a known-good and a known-bad case first. A metric that cannot separate two cases whose answer you already know is an opinion, and it will justify the wrong change — smoothness metrics reward blurring, coverage metrics quietly measure the wrong denominator.
- **A checker is a metric.** A script reporting "this string is absent", "no call sites remain", "nothing matched" is measuring: point it first at something you can see with your own eyes and confirm it says *present*. Its false negatives are the dangerous half — an empty finding list reads as diligence, and a clean report cannot distinguish "nothing is wrong" from "the check could not see". A checker that has only returned findings you liked has been agreed with, not validated.
- **Search for something only your change could have produced.** Confirming an edit reached a build output fails in its own way: ordinary tokens already exist in the project, so the search succeeds against code that predates you when nothing was rebuilt. Pick a string unique to the change, and confirm the string it *replaced* is gone, which no pre-existing match can fake. Match the emitted form — build steps escape, rename, minify and split — and read the artifact the consumer actually loads, not an older build beside it.
- **Establish that a movement is real before investigating its cause.** At small per-bucket counts, ±25% between adjacent days or segments is ordinary. Size the noise first, then hunt. Ruling out five mechanisms for something that never exceeded noise is the most expensive route to "it was nothing", and each eliminated cause makes the movement feel more established when nothing has been.
- **An aggregate can be significant while every component of it is noise.** Split a headline result by the dimensions the change acts on, and by time, before believing it. Components near the threshold that flip sign between adjacent periods are independent wobbles that happened to align. Where the aggregate mixes populations the change treats differently, it conflates "did the change work" with "did it cover the same ground", and the split answers both.
- **When a metric looks wrong, check the metric's configuration before changing the code it measures.** A missing signal, a population that should not be there, a number that cannot be right — far more often the measurement's setup (which event it counts, how it dedupes, which environment it reads) than the instrumented code. Planning a refactor from the symptom risks rewriting working code to satisfy a misconfigured reading.
- **A value your own harness wrote is not an observation.** Probes, fixtures and repro scripts mutate what they inspect — seeding a field, clearing a key, stubbing a getter — and the reading that comes back is your own input echoed. It bites twice: reporting the injected value as a discovery, and generalising from a wipe you performed to a claim about the system. Name who last wrote a value before it becomes a finding; re-derive from an untouched path.
- **The user's direct observation outranks the metric.** If someone looks at the output and says it got worse while the number says better, the number is wrong until proven otherwise. Go find what it is failing to capture.
- **Two numbers are only comparable if they were computed the same way.** Before setting a fresh measurement against an existing figure — a documented baseline, a number in a ticket, last quarter's result — confirm both share a denominator, a population and a time window. A raw event count is not a per-user rate; a one-week slice is not 90 days; an unfiltered query is not one excluding test accounts. Getting this wrong yields a confident "it's actually X, not Y" that can redirect real work. If you cannot reconcile them, report the new number with its definition and say the comparison is unavailable.
- **Change one variable per measurement.** Two changes measured together give a delta you cannot attribute, and the improvement gets credited to whichever one you were hoping for.
- **A commit justified by a measurement contains only what was measured.** Bundling an unmeasured change alongside is how a change already measured as *worse* ships anyway.
- **A number written into a durable artifact is held to a higher bar than one said in passing.** Tickets, write-ups, PR bodies and dashboards are quoted onward long after the caveats are lost. Decompose it first, or write the range and the method instead of the point estimate.
- **A measurement that says "worse" is a result, not a setback.** Revert it there and then. Do not carry it forward hoping a later change compensates.
- **A rule set that classifies real data is derived from that data, never from a description of it.** Filters, matchers, parsers and heuristics written from a ticket's prose, a remembered payload shape or an upstream changelog miss the cases nobody described — and pass their tests, because the fixtures were invented from the same guess. Pull a representative sample, group it by frequency, write the patterns against that, and build fixtures from real records, including ones that must *not* match. A classifier whose suite contains no real input has been specified, not verified; the sample also catches a precise-looking pattern that matches nothing.
- **A value read off one instance cannot tell you whether it is absolute or derived.** At one instance a fixed quantity and a computed one are indistinguishable, and the coincidence reads as confirmation: exactly half its container looks like a ratio, a ratio landing on a round number looks like a constant. Implement the wrong one and it is right only at the instance you opened. Check a second instance at a different size; with only one, implement the reading that degrades safely (a cap rather than a hard size) and state the assumption where the next reader will meet it.
- **A test that encodes a product judgment is a metric, and gets validated like one.** When an assertion says a *behaviour* is correct ("one result here is the right number"), that claim came from you, not the code — writing it down freezes it. Check it against real data first. This is the most dangerous item on the list, because the suite goes green and every later review reads the assertion as the specification.

**Under an unknown cause, prefer the fix that removes the failing component to the one your theory predicts.** A remedy derived from an unconfirmed mechanism inherits all of its uncertainty, and each attempt spends a deploy, a release window and somebody else's afternoon — while a failure teaches little, because it cannot say which premise was wrong. Say which kind of fix you propose: one that depends on the diagnosis, or one that holds whichever diagnosis is right, such as routing around the failing component or switching off the optional step that fails. Verify the end state on the live system *before* shipping — a route-around's destination is usually already reachable. When a handed-over remedy fails, re-derive the model instead of offering the next theory-derived fix; the second failure says the model is wrong, not the parameters.

## Exploration guard rails

For open-ended tasks, explore briefly, then start writing code — partial progress beats perfect plans. Never spend an entire session on analysis without producing a working artifact.

Producing one artifact does not buy unlimited exploration afterwards. Investigation continues one cheap-sounding step at a time while the total quietly runs into hours. After a few rounds with nothing further shipped, state the cumulative cost and what is left untested, and ask whether to continue — rather than offering the next step as though it were the first.

**When the next step spends the user's time instead of yours, that check is due immediately, not after a few rounds.** Each handed-over step — run this, click that, paste the output — reads as small to whoever proposes it and lands as an interruption on whoever performs it. The tell is a second consecutive round ending by asking them to go and try something. Say what has been spent, what it ruled out, and what the alternative route costs, then let them choose; if the approach was wrong, lead with that rather than the next refinement.

**The same count applies when they are the only one who can see the result.** Tuning anything judged by eye — spacing, sizing, position — against a rendered artifact you cannot open turns every attempt into a round trip that looks like one small adjustment rather than the tenth. The loop hides its own failures: a change that did not take and one that took but looked wrong come back as the same report. After the second such round, get yourself a way to see it, or say plainly that you are guessing.
